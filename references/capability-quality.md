# 能力积木判定规则

生成或修改能力积木时，对每块按六项各记 0–2 分；默认不向用户展示分数。

| 维度 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| 证据可追溯 | 具体行动/判断与产出可定位 | 有经历但链条缺一环 | 只靠标签或推测 |
| JD 相关 | 对应该岗位被雇来完成的核心闭环，且市场持续购买这组能力 | 能力有用但只覆盖局部，或市场证据较弱 | 仅为 incidental skill，或与目标岗位无关 |
| 结果链 | 行动、方法/范围、产出/影响完整 | 有行动与产出但关系较弱 | 只有职责描述 |
| 可复用性 | 能跨任务或环境重复创造结果 | 只在相近场景迁移 | 单次任务/工具名 |
| 边界准确 | 包装有力且责任、数据、因果准确 | 基本准确但范围模糊 | 抬高所有权或影响 |
| 密度与区分 | 每句增量明确且与其他积木不重叠 | 有轻微复述或空词 | 冗长、同义重复 |

**Accept**：总分至少 10，且无硬伤。  
**Revise**：8–9 分或局部证据/表达可修。  
**Reject**：7 分以下，或出现任一硬伤。

硬伤：虚构事实或数字；把参与写成独立负责；制造未经支持的因果或影响；把单份 JD 词、工具名或宽泛性格词直接当能力；同一证据被包装成多块重复积木。

评分后必须做组合检查：逐块合格不等于整组合格。若两块的主要行动、结果和 JD 需求簇中有两项相同，优先合并；只有方法不同且能独立迁移到不同业务问题时才保留。整组通常 2–4 块，数量不足不构成缺陷，重复凑数直接 `Revise`。

## 后台排序

按以下顺序比较并用 A、B、C、D 标记，A 为当前目标下优先级最高：

1. 是否命中目标市场 2–3 个常见岗位反复出现的核心工作；
2. 证据链是否完整、可靠且能清楚归因于用户；
3. 能否跨公司、行业或相近岗位继续解决同类业务问题；
4. 在满足前三项后，是否形成区别于普通候选人的能力优势。

排序是相对于当前目标岗位的使用优先级，不是对用户能力高低的永久评价。评分、排序依据、置信度和“为什么排第几”仅后台维护，不出现在用户层。

## 岗位覆盖与组合

- 单块`适配岗位`回答“这块能力能为哪些常见岗位提供实质证据”，不是重复整组的目标岗位。
- “市场常见岗位”按三层 Gate 判断：
  1. **Core Work Gate**：该能力是岗位被雇来完成的核心工作，不只是岗位偶尔会用到的附带技能。
  2. **End-to-End Contribution Gate**：该积木能独立覆盖一个有意义的 `problem → judgment/work → recognizable output` 工作闭环，而不只是为岗位提供局部帮助。
  3. **Hiring Legibility Gate**：即使具体 title 随公司漂移，目标市场仍存在雇主持续为这组能力与价值闭环招聘的岗位族。
- 三层 Gate 用来排除牵强映射，不要求每项都以最严格方式同时成立。前两项明确且第三项有多份 JD 或稳定岗位族支持时可直接列入；相邻岗位若映射合理但仍需市场验证，可在不挤占核心岗位的前提下保留，不能因为采用 Gate 而把用户锁定在最保守方向。
- 若所有积木都出现完全相同的岗位列表，重新检查是否遗漏了相邻岗位价值，或是否把方法关键词误当成了岗位；没有真实扩展时允许重复，不能硬造多样性。
- 组合岗位必须由至少两个互补能力共同支持。例如一块提供研究与洞察，另一块提供原型与产品判断，组合后才可以支持产品经理方向。
- 组合只保留目标市场中常见且有多份 JD 支持的岗位名称，最多三组；稀有 title、团队内部称谓和过度细分名称不输出。
- 岗位覆盖只表示能力证据可迁移，不等同于用户已经满足年限、学历、行业或职级等全部招聘条件。

## 高密度写法

证据链优先压缩为：`<问题/约束> → <关键判断与行动> → <可核验产出/影响> → <能力结论>`。只保留支持推导所需的事实，不罗列完整项目过程。

职业包装可以改变信息顺序、能力命名和动词强度，但强动词必须匹配真实权限。没有增长数据时，使用样本量、覆盖范围、交付节点、采用对象、决策影响或具体产物；不要用“显著提升”“广受好评”等不可核验句子补位。

## 快速反例

- 较弱：`沟通能力强，熟练使用 Notion，参与多个项目。`
- 较好：`多方目标不一致 → 建立统一需求台账和评审节点 → 3 个并行项目按期交付 → 形成跨团队交付编排能力。`

较好的版本命名了可重复结果，用方法、规模和结果支撑关键词；较弱版本只有性格、工具和参与描述。
